# Karpathy × ELI5：三個示範

> 以下都是**合成情境**，用來展示技能的輸出樣式；不是任何真實專案的調查結論。實際使用時，技能會先讀來源，再把結論接回原始檔案、行號與測試。

## 範例一：新工程師接手 API 的 403

**輸入**：「使用者明明登入了，為什麼 `GET /reports/42` 回 403？請給新進工程師看。」

**30 秒版**：登入像進大樓的門禁卡；403 表示你進了大樓，但這張卡不一定能開第 42 號檔案室。別把『有登入』誤當『有權讀這份報告』。

**圖解**：`請求 → 驗證身分 → 查報告所屬帳戶 → 授權檢查 → 200 或 403`。若報告根本不存在，是否回 404 而非 403，取決於實際 API 契約，不能靠類比決定。

**深入**：先核實中介層是否帶入身分、資源查詢是否依租戶／所屬帳戶限制，再看拒絕時的狀態碼規則。測試至少涵蓋自己的報告、別人的報告、未登入、報告不存在。**不得**用「只要登入就放行」修 403。

## 範例二：前端草稿為何可能消失

**輸入**：「送出失敗後草稿有時消失，請畫資料流並告訴我哪裡有風險。」

**30 秒版**：像寫信時按寄出：郵差沒收到，不代表你可以把唯一草稿丟掉。要等伺服器確認，或確認另有可靠副本，才處理本機草稿。

**圖解**：`編輯 → 本機草稿 → 送出 → {伺服器確認 → 清除草稿；送出失敗 → 保留草稿並提示}`；如果有離線佇列，還須證實佇列**真的寫入成功**。

**深入**：找出清除草稿的位置、網路回應與本機儲存的先後順序、重複點送出的競態。驗收：讓網路和離線儲存同時失敗，仍能找回唯一草稿。此處的「可靠副本」必須以實測定義，不能只看函式名稱。

## 範例三：CI 紅燈是否代表程式壞了

**輸入**：「同一 commit，Node 22 測試逾時，Node 24 通過。幫我理解風險和下一步。」

**30 秒版**：兩位考官用同一份考題，一位說時間到了，一位說通過；這不是程式正確或錯誤的充分證明。先找到是否有時序依賴。

**圖解**：`相同 SHA → {Node 22: timeout；Node 24: pass} → 對照時間、重跑與分離測試 → 分類原因`。

**深入**：核對兩個 job 確實測同一 SHA、失敗是否只由超時造成、測試是否依賴真實時間／外部服務／平行負載。重跑通過只能提示「可能不穩定」，不能替代根因或把 CI 宣稱全綠。

---

實際呼叫範例：

> 用 karpathy-explain 解釋這段原始碼給剛接手的工程師。先做 30 秒摘要，再畫成功／失敗流程，最後列出已確認與待驗證內容；請附檔案與行號：`〈來源路徑〉`。
