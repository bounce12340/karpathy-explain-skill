# 輸出模板與證據標記

需要穩定格式時使用。依任務刪減段落，不必每段都寫；以使用者語言輸出（下方標籤可翻譯）。

## 證據標記

每個重要結論後加一個標記，讀者一眼可知可信度：

| 標記 | 意義 | 例子 |
|---|---|---|
| `[已確認]` | 原始碼／文件中看得到，附位置 | `[已確認 auth/middleware.ts:42]` |
| `[實測]` | 實際執行、測試或 log 證實 | `[實測 npm test auth.spec]` |
| `[推論]` | 由已知證據推得，尚未證實 | `[推論：依函式名稱與呼叫順序]` |
| `[未知]` | 讀不到或無法判斷，說明缺什麼 | `[未知：未提供 gateway 設定]` |

英文：`[confirmed]` `[tested]` `[inferred]` `[unknown]`。圖表節點同樣標記；推論用虛線。

**錨點格式**：已確認的結論寫成 `[已確認 路徑:行號]` 或 `[confirmed path:start-end]`，路徑相對於 repo 根目錄。這個格式可被機器檢查（本 repo 的 `scripts/validate.py` 會驗證檔案與行號存在）；放在反引號內則視為格式示意，不檢查。行號會隨程式變動，交付時以當下版本為準；若可能，附 commit SHA。

**誠實界線**：錨點只證明「那一行存在」，不證明那一行仍支持你的說法。重要結論請在說明中引用該行的關鍵片段。

## 回覆骨架

```markdown
## 30 秒
一句話：〈它做什麼、為誰解決什麼〉
比喻：〈生活類比〉——但〈比喻在哪裡不成立：程式碼的具體行為〉[已確認 路徑:行號]（找不到對應程式碼就標 [推論]）。

## 3 分鐘：資料怎麼走
〈圖解：能渲染就用下方 Mermaid，終端機用 ASCII 圖〉
- 成功：〈路徑與結果〉[標記]
- 失敗：〈路徑、錯誤處理、使用者看到什麼〉[標記]
- 常見誤解：〈一句話〉

## 深入
| 先看這裡 | 為什麼 |
|---|---|
| `路徑:行號` | 〈這裡決定了什麼〉 |

邊界與風險：〈權限／資料遺失／競態／資安／效能，只寫相關的〉
驗證方法：〈可重現的指令或測試情境〉

## 未確認清單
- 〈假設〉：要確認請〈做什麼〉
```

## Mermaid 圖解模板

```mermaid
flowchart LR
  A[請求進入] --> B{驗證身分}
  B -- 成功 --> C[查詢資料歸屬]
  B -- 失敗 --> X[401]
  C --> D{有讀取權限?}
  D -- 是 --> E[200 回傳]
  D -- 否 --> F[403 拒絕]
  C -.推論.-> G[(快取?)]
```

規則：成功與失敗路徑都要畫；推論用 `-.->` 虛線；節點不超過約 12 個，超過就拆圖；圖下方附一段等價純文字，供無法顯示圖的讀者使用。

## ASCII 圖解模板

終端機、純文字訊息和不會渲染 Mermaid 的環境用這個。同一個流程：

```text
請求進入
   |
   v
驗證身分 --失敗--> 401
   |
  成功
   v
查詢資料歸屬 - - 推論 - -> 快取？
   |
   v
有讀取權限？ --否--> 403 拒絕
   |
  是
   v
200 回傳
```

規則：每行不超過約 60 欄，避免換行把圖弄亂；成功與失敗路徑都畫；推論用 `- - ->` 虛線並標「推論」；超過約 12 個節點就拆成兩張圖。

## 讀者自測（交付前自己先答一次）

1. 資料從哪裡來？
2. 成功時去哪裡？
3. 失敗時怎麼辦？
4. 哪些結論還沒確認？
5. 要修改時先看哪裡？
6. 比喻的失效點有對到哪一行程式碼？沒有的話，有標成推論嗎？

任何一題答不出來，或答案沒有證據標記，就補上或明說未知。
