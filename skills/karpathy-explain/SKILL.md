# Karpathy × ELI5：工程理解階梯

以 Karpathy 2026-10-02 的[貼文](https://x.com/karpathy/status/2105819303471976479)為靈感：文字 → 圖／圖片 → 可互動網頁 → 客製解說影片。這是呈現策略，不是 Karpathy 官方技能，也不代表他保證能降低理解時間。若本機另有 `eli5` 技能，可用它校準對象與語氣；若有 `frontend-design` 技能，可用它檢查網頁視覺品質。**即使沒有這兩個技能，本檔仍可獨立運作**：遵守下面的分層說明與可用性要求即可。

## 接收任務

讀取使用者提供的原始碼、文件、錯誤、log 或 URL（需上網時使用可用的網頁存取工具）；不憑檔名猜內部行為。確認對象、理解任務（例如「我今天要修這個 bug」）、已知基礎和可交付格式。資訊不足且不影響開始時，用預設：對象是接手陌生程式的工程師、以使用者語言回覆、簡短文字＋一張圖；只有關鍵材料缺失才詢問。

## 先建立可信的事實卡

先在心中或工作檔列出：
- 一句話：系統做什麼、為誰解決什麼問題。
- 實際路徑：觸發 → 中間資料／狀態 → 輸出；在每個關鍵節點附來源（路徑:行號、函式、文件段落或 log）。
- 不可省略的邊界：權限、資料遺失、失敗處理、競態、資安、效能與未知點，只寫相關者。
- 使用者完成任務必須知道的 3 個觀念與下一個可驗證動作。

區分「原始碼可見」「實測」「推論」「未知」。無法讀到依賴、服務或 runtime 時明說；圖表不可把推論畫成既定事實。不可把機密值或私人資料放進圖／網頁／影片／範例。

## 依 ELI5 分層，不把工程師當小孩

若已安裝 `eli5`，先讀其 `SKILL.md`；否則直接依對象調整語氣、類比與術語。工程師預設三層，可讓讀者自行停在任一層：
1. **30 秒**：一句話、目標、生活類比、結果；類比後立即指出在哪裡失效。
2. **3 分鐘**：帶箭頭的真實資料流、一次成功與一次失敗、最常見誤解。
3. **深入**：原始碼位置、狀態/介面、邊界與取捨、可重現檢查。

技術詞首次出現用一句話定義；不用空泛的「這很簡單」。簡化句須仍然為真，尤其不能省略授權／隱私／風險；以可回到原始碼的錨點保留精確性。沒有量測不得聲稱節省多少時間或「大幅降低」已實證。

## 選呈現形式（逐級增強，不必每次全做）

| 條件 | 產物 | 要求 |
|---|---|---|
| 短問題／需要快讀 | 簡明文字 | 先結論、再例子、再風險／下一步；可請求「以 ASD-STE100 風格／約 80% 嚴格度」寫短句，**不是**宣稱符合正式規範 |
| 跨兩個以上元件／有分支 | 圖解 | 用 Mermaid 或 HTML/SVG 寫來源標籤、成功與失敗路徑；另附純文字等價說明 |
| 需要點開不同層級／情境切換 | 自包含 HTML | 行動版、鍵盤可用、可見 focus、尊重 reduced-motion；禁止預設外部 CDN；給可下載檔 |
| 有時間軸／空間過程、使用者明確要影片 | 分鏡 → 可播放檔 | 先確定旁白來源、授權、成本、長度；沒有 API key 不假裝生成，優先本機可用工具。避免直接仿製 3Blue1Brown 的獨有視覺元素或聲音 |

選最便宜而能解決理解任務的形式。可附「再深一層」入口，但不為炫技做影片。建立檔案後實際預覽／測試；若圖或網頁只有裝飾而無資訊增益，退回文字。

## 自我驗收

請讀者能回答：「資料從哪裡來？成功時去哪裡？失敗時怎麼辦？哪個結論是尚未確認？我要改動時先看哪裡？」逐項回對原始證據；示例不可假冒專案實況。演示資料一律標註為合成。提供來源連結、推論與未驗證清單，避免漂亮圖示造成虛假的確定感。

## 可直接使用的請求

「用 karpathy-explain 解釋這段程式給剛接手的工程師：先 30 秒 ELI5，再畫成功／失敗資料流，最後指出 3 個值得看原始碼的位置與尚未驗證的假設。來源：〈檔案或網址〉。」
