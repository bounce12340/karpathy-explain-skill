# Karpathy × ELI5：工程理解階梯

以 Karpathy 2026-10-02 的[貼文](https://x.com/karpathy/status/2105819303471976479)為靈感：文字 → 圖／圖片 → 可互動網頁 → 客製解說影片。這是呈現策略，不是 Karpathy 官方技能，也不代表能保證縮短理解時間。本檔可獨立運作；若另有 `eli5` 或 `frontend-design` 技能，可輔助語氣校準與網頁設計。

**以使用者的語言回覆**（本檔以繁體中文撰寫不影響輸出語言）。

## 快速模式

使用者只要快速理解、或問題很小時：只給「30 秒」＋「下一步看哪裡」＋「未確認清單」，不畫圖、不做網頁。使用者說「深入」「完整版」或需要修改程式時，才展開全部層級。

## 接收任務

讀取使用者提供的原始碼、文件、錯誤、log、diff 或 URL；不憑檔名猜內部行為。確認對象、理解任務（例如「今天要修這個 bug」）、已知基礎與交付形式。資訊不足但不影響開始時用預設：對象是接手陌生程式的工程師、簡短文字＋一張圖；只有關鍵材料缺失才詢問。沒有任何來源時，回答必須標明是「一般性說明／假設示範」，不是對該專案的結論。

## 先建立可信的事實卡

先列出：
- 一句話：系統做什麼、為誰解決什麼問題。
- 實際路徑：觸發 → 中間資料／狀態 → 輸出；關鍵節點附來源（路徑:行號、函式、文件段落或 log）。
- 不可省略的邊界：權限、資料遺失、失敗處理、競態、資安、效能，只寫相關者。
- 讀者完成任務必須知道的 3 個觀念與下一個可驗證動作。

每個重要結論加證據標記：`[已確認]` `[實測]` `[推論]` `[未知]`（英文 `[confirmed]` `[tested]` `[inferred]` `[unknown]`），規則見 [references/output-template.md](references/output-template.md)。讀不到依賴、服務或 runtime 時明說；圖表不可把推論畫成事實。不把密碼、金鑰、個資放進圖／網頁／影片／範例。

## 依 ELI5 分層，不把工程師當小孩

依對象調整語氣、類比與術語。工程師預設三層，讀者可停在任一層：
1. **30 秒**：一句話、目標、生活類比、結果；類比後立即指出在哪裡失效。
2. **3 分鐘**：真實資料流、一次成功與一次失敗、最常見誤解。
3. **深入**：原始碼位置、狀態/介面、邊界與取捨、可重現檢查。

技術詞首次出現用一句話定義；不說空泛的「這很簡單」。簡化句仍須為真，不能省略授權、隱私或風險。未量測不得宣稱節省多少時間。

## 寫作規則（改編自 ASD-STE100）

文字層依下列規則寫，細節與正反例見 [references/writing-rules.md](references/writing-rules.md)：
1. **說出誰做了什麼**：主動語態，寫出主詞與原因；不寫「檔案沒有被推上去」。
2. **一詞一義**：一個概念在整段解說只用一個詞；可能有兩種意思的詞（如「測試」「LLM」）要點名是哪一個。
3. **一段一個主題，先給結論**。
4. **一句一個問題，用肯定問句**：需要讀者決定時用編號問題；不用「不是…嗎？」。
5. **不省略句子成分**：狀態寫成完整句子，分清「還沒做」與「刻意不做」。
6. **描述句短**：英文不超過 25 詞（STE 規定）；中文約 40 字（經驗值）。

這是改編，不是 STE 合規；STE 受控字典只適用英文，不套用在中文回覆。

## 選呈現形式（逐級增強，不必每次全做）

| 條件 | 產物 | 要求 |
|---|---|---|
| 短問題／需要快讀 | 簡明文字 | 先結論、再例子、再風險／下一步；依上方寫作規則，**不**宣稱符合 ASD-STE100 正式規範 |
| 跨兩個以上元件／有分支 | 圖解 | 優先 Mermaid（模板見 references）；成功與失敗路徑都畫，推論用虛線；附等價純文字 |
| 需要切換情境或展開層級 | 自包含 HTML | 單一檔案、無外部 CDN；手機可讀、鍵盤可用、可見 focus、尊重 reduced-motion |
| 有時間軸／空間過程，且使用者明確要影片 | 分鏡 → 可播放檔 | 先確認旁白來源、授權、成本、長度；沒有工具或 API key 就只交分鏡，不假裝已生成。不仿製他人獨有的視覺風格或聲音 |

選最便宜而能完成理解任務的形式。做完實際預覽；圖或網頁若沒有增加資訊，退回文字。

## 常見情境的重點

- **審查 AI 產生的程式／PR**：先列「改了什麼行為」而非「改了哪些檔案」；標出沒有測試覆蓋的新分支、被刪除的檢查、權限與錯誤處理變化。
- **錯誤／log**：從第一個真正的錯誤開始，不從最後一行；區分根因與連鎖錯誤。
- **接手模組**：入口在哪、資料存哪、誰呼叫它、改了會影響誰。

## 交付前自我驗收

讀者應能回答：資料從哪裡來？成功時去哪裡？失敗時怎麼辦？哪些還沒確認？要修改先看哪裡？任一題答不出或沒有證據標記，就補上或明說未知。示範資料一律標註為合成。引用行號時用可檢查的錨點格式 `[confirmed 路徑:行號]`，並先重新讀一次該行確認內容沒變。

## 範例請求

「用 karpathy-explain 向剛接手這個模組的工程師解釋〈檔案〉：先 30 秒摘要，再畫成功與失敗路徑，最後列出 3 個該看的原始碼位置和尚未驗證的假設。」

「用 karpathy-explain 快速模式，告訴我這個 PR 改變了什麼行為、有什麼風險。」
